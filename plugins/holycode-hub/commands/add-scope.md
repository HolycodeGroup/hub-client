---
description: Add a story to the linked Hub project's backlog, or edit or delete an existing one — authored on the Hub, not a local file
argument-hint: <story description> | edit <story-id> <what changes> | delete <story-id>
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps.
3. **Edit mode** — when `$ARGUMENTS` starts with `edit <story-id>`: call the `project_status` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>" }` and take that story's row (title, points, priority, deps, screen, its epic id and its `version`); build ONLY the changed fields (`title`, `description`, `acceptance_criteria`, `points`, `priority`, `deps`, `screen`, `doc_impact`, or `epic_id` of the same project) — a text or list field replaces the stored one wholesale, so write it in full (the board does not return description / acceptance criteria: take the current text from the user or the authoring source); show a before/after diff and ask ONE confirmation.
4. On yes, call the `project_story_update` tool once with `{ "project_id": "<that id>", "story_id": "<story-id>", "version": <the fetched version>, ...the changed fields }`; a `409` means the story changed since you read it — re-fetch `project_status` and re-show the diff, never blind-retry; a `422` (`BUSINESS_STORY_CLAIMED` / `BUSINESS_STORY_COMPLETED` / `BUSINESS_PROJECT_ARCHIVED`) means report it and stop — a completed story's new scope is a new story. Report the story_id and new version, then stop.
5. **Delete mode** — when `$ARGUMENTS` starts with `delete <story-id>`: call the `project_status` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>" }` and take that story's row (id, title and its `version`) — if it is not on the board, report that and stop; show its id and title and ask ONE explicit confirmation (it leaves the status board, estimates and the claim pool; its history is kept). On yes, call the `project_story_delete` tool once with `{ "project_id": "<that id>", "story_id": "<story-id>", "version": <the fetched version> }`; a `422` `BUSINESS_STORY_HAS_DEPENDENTS` names the stories that depend on it — show those ids and stop (remove the dependency with `edit` first); a `409` means it changed since you read it — re-fetch `project_status` and re-confirm, never blind-retry; any other `422` (`BUSINESS_STORY_CLAIMED` / `BUSINESS_STORY_COMPLETED` / `BUSINESS_PROJECT_ARCHIVED`) means report it and stop. Report the deleted story_id, then stop.
6. **Add mode** (anything else): run `/holycode-hub:guidance story template` to get the story shape (persona-form story, testable acceptance criteria, Fibonacci estimate), then build from `$ARGUMENTS` the input `{ "phase": { "name", "priority" }, "epic": { "name", "priority" }, "story": { "title", "description", "acceptance_criteria", "priority", "points", "deps", "doc_impact", "repository_id" } }`. **Documentation impact:** propose `doc_impact` — the project documents the story's completion will change (`PRD`, `ARCHITECTURE`, `TECHNICAL_SPEC`, `API_SPEC`, `SCREENS`, `DECISIONS_AND_CONSTRAINTS`, `GLOSSARY`; an endpoint usually changes `API_SPEC`, a screen `SCREENS`, a data-model or design change `TECHNICAL_SPEC` or `ARCHITECTURE`), `[]` when it changes none — and let the user confirm or change it. **Backend-first:** if this is a frontend (web/mobile) story that calls an HTTP endpoint, the backend story that OWNS that endpoint must come first — check the board (`project_status`) for it; if it does not exist, author that backend story FIRST and set this story's `deps` to it (the Hub then blocks claiming the frontend story until the backend one is completed). Name each dependency by its story key (for example `HH-391`) as `project_status` shows it — the Hub stores the story it names and refuses a key that matches no story of the project (`422 BUSINESS_STORY_DEP_UNKNOWN`). Never fold endpoint work into a frontend story, and never author a frontend story that silently assumes an endpoint with no owning story. A pure-UI story that calls no endpoint has no such dependency. **Repository — one story, one repository:** a story changes at most one repository. Read the project's repositories from `project_status` → `project.repositories` (each `id`, `kind`, `url` and `description`; a repository's name is the last segment of its URL path, without `.git`) and propose the repository from the work: an endpoint goes to a `BACKEND` repository, a screen to a `FRONTEND` or `MOBILE` one. When exactly one repository matches, propose it as `story.repository_id` (its id); when several match (several backend services, or several frontends such as customer-facing, back office and admin), list every candidate by name and description and ask which one — never pick one from the kind alone. A feature that spans repositories is never one story: author an epic with one story per repository, linked by `deps`, backend first. Leave `repository_id` out for work not tied to code (allowed), and in a project with a single repository (the Hub assigns that one). Show the built input to the user for confirmation before writing.
7. Call the `project_story_add` tool on the `holycode-hub` MCP server exactly once with `{ "project_id": "<that id>", ...the built phase/epic/story }`.
8. Report the returned story key (`key`, e.g. `HH-228` — the key the developer claims and writes in commits) with its story_id / epic_id / phase_id. Authoring writes no project documentation — documents change only when a story is delivered (/holycode-hub:complete). **Next step:** end your reply with one line that starts with `Next:` — `Next: /holycode-hub:status to see the story on the board, then /holycode-hub:claim <that key> once it is ready` (after an edit or delete, just `Next: /holycode-hub:status`). Make no further Hub calls for this step.
