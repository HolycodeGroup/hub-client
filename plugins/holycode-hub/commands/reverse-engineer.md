---
description: Plan the rebuild of a legacy codebase on a new stack — analyses the old code locally (it never leaves this machine) and publishes only the derived analysis to the Hub, which authors the backlog, documents and questions
argument-hint: <path to the legacy codebase> [target stack]
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project.
3. Take the first `$ARGUMENTS` token as the path to the legacy codebase (it may be outside this directory; when it is missing, ask for it) and the rest as the target stack; when no target stack is given, call the `project_status` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>" }` and use `result.project.stack`. Then call the `work_guidance` tool once with `{ "project_id": "<that id>", "question": "reverse-engineering" }` and follow the returned `reverse-engineering` checklist in every step below.
4. Analyse the legacy codebase locally and READ-ONLY — never modify it and never copy it into this repository — running every pass of the checklist. On a large codebase you may split the work across read-only sub-agents, one per module, each returning only derived descriptions. Never put source code, secrets or personal data into the analysis.
5. Ask the user about the ambiguities the analysis raised, grouped by priority (P0 first); every question the user skips goes into `unresolved_questions`, naming the modules it blocks. Assemble the analysis `{ "source_stack", "target_stack", "modules", "data_model", "integrations", "findings", "unresolved_questions" }` exactly as the checklist describes.
6. Show a summary — the modules, the findings by severity, the stories the Hub will plan (a foundation phase plus one story per module) and the open questions — say plainly that no source code is sent, only these descriptions, and ask ONE confirmation.
7. On yes, call the `project_reverse_engineer` tool on the `holycode-hub` MCP server exactly once with `{ "project_id": "<that id>", "analysis": <the assembled analysis> }`. A `409` `CONFLICT_PROJECT_NOT_EMPTY` means the project already has a backlog — a rebuild plan only bootstraps an empty project: tell the user and stop. A `400` (`VALIDATION_SOURCE_CODE` names the field that looked like code; `VALIDATION_TOOL_INPUT` a malformed field) or a `422`: report the Hub's message and stop. Never retry.
8. Report the returned summary: the phases, epics and stories created, the documents written, the findings by severity and the questions opened (answer them with `/holycode-hub:resolve-questions`); the backlog lives on the Hub — view it with `/holycode-hub:status`. Make no further Hub calls for this step.
