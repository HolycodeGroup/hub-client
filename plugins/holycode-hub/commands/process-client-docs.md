---
description: Extract requirements from client documents and author them into the linked Hub project's backlog — on the Hub, not local files
argument-hint: [input-path]
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project.
3. Run `/holycode-hub:guidance story template` for the story shape, then read the client documents under `.project-management/input/client-input/` (or the path in `$ARGUMENTS`) and extract requirements into candidate phase/epic/story items, each with a proposed `doc_impact` (the documents its completion will change: `PRD`, `ARCHITECTURE`, `TECHNICAL_SPEC`, `API_SPEC`, `SCREENS`, `DECISIONS_AND_CONSTRAINTS`, `GLOSSARY`; `[]` for none) — English only, replacing any personal names with role labels; where a requirement is ambiguous, record it as an open question via `/holycode-hub:add-scope` rather than guessing.
4. Run `/holycode-hub:status` first and skip any candidate whose title already exists under the same epic with the same points and acceptance criteria (idempotent — re-running never duplicates a story); when the title matches but its points or acceptance criteria differ (a changed spec), do NOT skip it silently — offer "update existing" and, on yes, call the `project_story_update` tool once for that story with `{ "project_id": "<that id>", "story_id": "<id>", "version": <its version from the status board>, ...only the changed fields }` (`409` → re-fetch the board and re-show, never blind-retry; `422` → report and skip).
5. **Backend-first ordering:** before writing, order the candidates so that for any frontend (web/mobile) story calling an HTTP endpoint, the backend story that OWNS that endpoint is authored first and the frontend story carries it in `deps` (the Hub then blocks claiming the frontend story until the backend one is completed). If an endpoint has no owning backend story among the candidates or already on the board, author that backend story — never let a frontend story assume an endpoint that no story delivers. A pure-UI candidate that calls no endpoint has no such dependency. Show the ordered candidates to the user for confirmation before the first write, then write them with the `project_stories_add` tool on the `holycode-hub` MCP server (HH-95) — `{ "project_id": "<that id>", "idempotency_key": "<a fresh UUID v4>", "stories": [ { "phase": {...}, "epic": {...}, "story": {...with deps} } ] }`, at most 50 stories per call, all written or none. Write in dependency order: a story whose `deps` names a candidate of this run goes in a LATER call, once the call that wrote that candidate has returned its id. Generate a new key per call and reuse it only to retry that same call (the Hub replays the result, never duplicating); a refusal names the item (`stories[3].story.title`) — fix that item and retry the call.
6. Report how many stories were authored and any open questions recorded. **Next step:** end your reply with one line that starts with `Next:` — `Next: /holycode-hub:resolve-questions` when open questions were recorded, otherwise `Next: /holycode-hub:status to see the ready stories, then /holycode-hub:claim the first`. Make no further Hub calls for this step.
