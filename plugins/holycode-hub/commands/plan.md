description: Plan the linked Hub project from a client brief — scope, phased backlogs, technologies, constraints
argument-hint: <path-to-brief>
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps.
3. Take the brief file path from `$ARGUMENTS` (ask for it if none was given). If it is a document (PDF/DOCX) or a large text/markdown file, UPLOAD it instead of extracting locally: base64-encode the raw bytes and call the `project_document_upload` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>", "filename": "<name.ext>", "content_base64": "<bytes>" }`; on `status: "FAILED"` report the `failure_reason` and stop (convert PPTX/images to PDF and retry). Otherwise, for a small plain-text/markdown brief you may skip the upload and pass the text inline.
4. Call the `project_plan` tool on the `holycode-hub` MCP server exactly once — with `{ "project_id": "<that id>", "upload_id": "<the id from step 3>" }` when you uploaded, or `{ "project_id": "<that id>", "brief": "<the brief's full text>" }` for a small inline brief. Never both.
5. Report what the Hub returned (summary and open questions). The phased backlog now lives on the Hub — view it with `/holycode-hub:status`, never a local file; `/holycode-hub:export` materialises scope, technologies and constraints only.
6. **Repository — one story, one repository:** call the `project_status` tool once and read `project.repositories` (each `id`, `kind`, `url` and `description`; a repository's name is the last segment of its URL path, without `.git`). With one repository or none, skip this step — the Hub gives a single repository's stories that repository itself. With several, the planned stories carry none yet: propose one per story from its work (an endpoint goes to a `BACKEND` repository, a screen to a `FRONTEND` or `MOBILE` one); when several match (several backend services, or several frontends such as customer-facing, back office and admin), list every candidate by name and description and ask which one — never pick one from the kind alone. Show the proposals as one table and, once confirmed, set each with the `project_story_update` tool `{ "project_id": "<that id>", "story_id": "<id>", "version": <its version from the board>, "repository_id": "<id>" }` (`409` → re-read the board, never blind-retry). Leave work not tied to code without one. A planned story that spans repositories is split with `/holycode-hub:add-scope` into one story per repository, linked by deps, backend first.
7. **Next step:** end your reply with one line that starts with `Next:` — `Next: /holycode-hub:resolve-questions` when open questions came back, otherwise `Next: /holycode-hub:status to see the ready stories, then /holycode-hub:claim the first`. Make no further Hub calls for this step.
