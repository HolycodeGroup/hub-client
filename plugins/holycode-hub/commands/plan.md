---
description: Plan the linked Hub project from the client's documents with your own model — scope, phased backlogs, technologies, constraints
argument-hint: [input-path]
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps.
3. **Source — the client's documents, on this machine:** read every document under `.project-management/input/client-input/` (or the path in `$ARGUMENTS`) — the same source `/holycode-hub:process-client-docs` reads. Read a PDF or a text/markdown file directly; turn a DOCX or PPTX into text locally first (for example `textutil -convert txt` on macOS, or `pandoc`) — never upload a document to the Hub. With no document there, ask the user where the client's documents are and stop.
4. Call the `work_guidance` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>", "question": "project-plan" }` and follow the returned `project-plan` checklist: build the `brief` (the client's requirements consolidated from all the documents, at most 200,000 characters — it becomes the project's PRD) and the `plan` `{ "files", "summary", "open_questions", "backlog" }` — the seven files, the backlog as data with every story's `doc_impact`, role labels instead of personal names. The plan is built here, with the user's own model — the Hub runs no model for it and needs no model account.
5. **Preview — nothing is sent before the user confirms:** show the phases, epics and stories as one table (title, priority, points, `doc_impact`), then the summary and the open questions, and ask ONE confirmation; on changes revise and show it again, on no stop and send nothing. On yes, call the `project_plan` tool on the `holycode-hub` MCP server exactly once with `{ "project_id": "<that id>", "brief": "<the brief>", "plan": <the plan> }`. A `400` or `422` names what the Hub refused (a field, a file, a story): fix that part, show the user what changed and ask again before resending — never resend the same plan. A `409` `CONFLICT_STALE_VERSION` means another plan of this project landed first: run `/holycode-hub:status` and ask before planning again.
6. Report what the Hub stored: the summary, the open questions and `backlog_result` (the phases, epics and stories created). When `backlog_result.skipped` is `PROJECT_HAS_BACKLOG`, the project already had stories, so only the plan files got a new version — add new requirements with `/holycode-hub:process-client-docs`. The phased backlog lives on the Hub — view it with `/holycode-hub:status`, never a local file; `/holycode-hub:export` materialises scope, technologies and constraints only.
7. **Repository — one story, one repository:** call the `project_status` tool once and read `project.repositories` (each `id`, `kind`, `url` and `description`; a repository's name is the last segment of its URL path, without `.git`). With one repository or none, skip this step — the Hub gives a single repository's stories that repository itself. With several, the planned stories carry none yet: propose one per story from its work (an endpoint goes to a `BACKEND` repository, a screen to a `FRONTEND` or `MOBILE` one); when several match (several backend services, or several frontends such as customer-facing, back office and admin), list every candidate by name and description and ask which one — never pick one from the kind alone. Show the proposals as one table and, once confirmed, set each with the `project_story_update` tool `{ "project_id": "<that id>", "story_id": "<id>", "version": <its version from the board>, "repository_id": "<id>" }` (`409` → re-read the board, never blind-retry). Leave work not tied to code without one. A planned story that spans repositories is split with `/holycode-hub:add-scope` into one story per repository, linked by deps, backend first.
8. **Next step:** end your reply with one line that starts with `Next:` — `Next: /holycode-hub:resolve-questions` when open questions came back, otherwise `Next: /holycode-hub:status to see the ready stories, then /holycode-hub:claim the first`. Make no further Hub calls for this step.
