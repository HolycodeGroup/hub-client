---
description: Set up Holycode Code Review for the linked Hub project — what each repository needs, the provider's steps and the Hub link that connects it (never a token in the chat)
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps.
3. Call the `project_code_review_status` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>" }`. The `result` is a JSON object; if it arrives as a text content block, parse that text as JSON first. If the Hub answers 403 `FORBIDDEN_RESOURCE`, tell the user this account cannot see that project's code review (a developer sees the projects they work on) and stop. When `result.availability` is `OFF`, say that code review is not switched on for this Hub and stop; when it is `UNAVAILABLE`, say that Holycode Code Review cannot be reached right now, show each repository's `last_known` status and stop; when `result.archived` is true, say the project is archived, so its reviews are stopped, and stop.
4. Present one line per repository: its `url`, its `provider`, its access (`access.status`: `public` or `ok` needs nothing, `unknown` is not connected yet, `lost` must be connected again, `expiring` is a token that expires on `access.expires_at` and should be replaced; add `access.method`) and its latest review (`latest_run`: status, score, findings and `report_url`). When `duplicate_of` is set, say it is the same repository as another entry and is reviewed there; when `unreadable` is true, say its status cannot be shown right now and point to `result.tab_url`; any other repository with `supported: false` needs an https or SSH address, changed on the project's Repositories tab in the Hub.
5. For each repository with `needs_access: true`, explain what to do from `recommended_method`, then open its link for the user with the system opener (`open` on macOS, `xdg-open` on Linux, `start ""` on Windows); always quote the link, as in `open "<link>"`, because a Hub link carries `&` that a shell would split at; and print the link too. `github_app`: when `connect.add_on_github` is set, the Holycode Code Review GitHub App is installed for `access.github_account` but does not include this repository, so open that link to add it on GitHub; otherwise open `connect.github` to install the app (or to connect GitHub again when `access.github_connect_again` is true); an access token through `connect.token` works too. `token`: walk the user through `guide` (`token_type`, `permission`, every entry of `steps` (where a step says "below", it means the Code Review page the link opens), `create_url` when set, `username_help` when `username` is `optional`, that they choose an expiry date themselves when `reads_expiry` is false, and `guide.alternative` when set as the other kind of token, with its own steps and a username that must be entered when its `username` is `required`), then open `connect.token`: the user pastes the token on that Code Review page. When `guide` is null, say the steps are on that page. **Never ask for, accept or repeat a token, password or key in this chat**: if the user pastes one anyway, do not use or repeat it, tell them to revoke it and create a new one, and point them back to the link.
6. Then wait for the user. When they say they are done, call `project_code_review_status` again with the same arguments (at most three times in this command) and report which repositories have access now; for one that still has `needs_access: true`, repeat its link and its `guide.failure_hint` when there is one.
7. **Next step:** end your reply with one line that starts with `Next:` — `Next: open <result.tab_url> to choose each repository's branch and schedule, then press Run now` when no supported repository has `needs_access: true` (an `expiring` token still needs replacing), otherwise `Next: finish connecting <that repository's url>, then tell me you are done`. When you stopped at step 3: after 403 `FORBIDDEN_RESOURCE`, `Next: ask the project's owner in the Hub to set up code review for it`; when the project is archived, `Next: open <result.tab_url> to read its past reviews; reviews resume once the project is unarchived in the Hub`; when the availability is `OFF`, `Next: ask your Hub administrator to switch on Holycode Code Review`; when the availability is `UNAVAILABLE`, `Next: run /holycode-hub:code-review-setup again once code review is available`. Make no further Hub calls for this step.
