---
description: Mark a claimed Hub story complete — anchor its commit, release the lease, record the completion
argument-hint: <story-key> [commit-sha] [--scope phase <name> | epic <name> | <story-key> … | code-review [--severity …]]
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" check`: for each story worktree it lists as expired, tell the developer the lease lapsed and offer to re-claim the story (`/holycode-hub:claim <key>`) or keep its branch (`node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" keep --key <key>`) — never delete one yourself.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps.
3. The first `$ARGUMENTS` token is the story key (e.g. `DHWH-7`; an old story id also works); the optional second is the commit sha — when absent, take the current commit from `git rev-parse HEAD`, and if that fails tell the user "Pass the commit sha: /holycode-hub:complete <story-id> <commit-sha>" and stop. Everything after a `--scope` token (the sha, when given, comes before it) is a standing-order scope: `phase <name>` → `{ "phase": "<name>" }`, `epic <name>` → `{ "epic": "<name>" }`, `code-review [--severity <a,b>]` → `{ "origin": "CODE_REVIEW" }` plus `"severity": [<each, UPPERCASE>]` when given, otherwise the story keys → `{ "stories": [<each key>] }`; send it as `"scope"` on the call below (omit it when there is no `--scope`). **Documentation first:** when the story you claimed declared documents (`story.doc_impact` in its claim response — none when `story.bug_doc_impact` is `CODE_NOW_MATCHES_DOC`), bring each one up to date with the code this story delivered BEFORE completing: run `/holycode-hub:generate-api-docs --story <key>` for `API_SPEC` and `/holycode-hub:generate-docs <document> --story <key>` for every other declared document — each publishes its document to the Hub for this story, sending only the `##` sections the story changed (the section form) and the whole document only when it is new or fully rewritten.
4. **Code-review stories** — when the story is a ticket made from a Code Review finding (its claim response had `story.origin` `CODE_REVIEW` and a `story.code_review` block), ask the developer ONE optional question first: was the finding's severity right — **AGREE**, **TOO_HIGH** or **TOO_LOW**? Add the answer to the call below as `"severity_assessment": "<that value>"` (it tells Code Review how well it judged the finding); omit it when they skip, and never send it on any other story. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/effort-capture.mjs" take` — it prints the effort measured since the last report as a JSON array (timestamps, actor and category only; never prompt text or code). When the array is non-empty, add it to the call as `"segments": <that array>` and do NOT send `human_ms` / `ai_ms`; when it prints `[]` or the command fails, use the estimate instead. Also run `node "${CLAUDE_PLUGIN_ROOT}/scripts/effort-capture.mjs" usage` — it prints the tokens this attempt used so far, per model, as a JSON array (counts only, never prompt text); when it is non-empty add it as `"model_usage": <that array>` (omit the field when it prints `[]` or fails). Otherwise estimate the human-vs-AI time split for this attempt (your best estimate in milliseconds — `human_ms` for the human thinking/deciding/reviewing, `ai_ms` for your generating; together ~the attempt's elapsed time), then call the `work_complete` tool on the `holycode-hub` MCP server exactly once with `{ "project_id": "<that id>", "story_id": "<story id>", "commit_sha": "<that sha>", "human_ms": <human estimate>, "ai_ms": <AI estimate> }` — it is an ESTIMATE, not a measurement; OMIT both fields if you genuinely cannot estimate (never send `0` / `0`). **Repository (HH-479):** when `.project-management/hub-pointer.md` carries a `**Repository ID:**` line, add `"repository_id": "<that id>"` to the call — the Hub records which repository the commit is in, so the story page can link it, and with a scope it hands out, and lists as next, only this repository's stories and stories with no repository (HH-477); omit the field when the pointer has no such line.
5. On success report the recorded commit, the completion time, and that the lease is released and the story is now `Completed`. When `result.standing_order` is present, list each `result.standing_order.handed_out` entry (`key — title`) as handed to the user next under the standing order (`/holycode-hub:claim <key>` returns its text), and say how many stories of the scope are still open (`result.standing_order.open`; 0 means the standing order is done). When `result.standing_order.quota_reached` is present, show its `message`: a claim limit held more stories of the scope back — a report, never a failure. Then ALWAYS end with what comes next, exactly as the Hub returned it in `result.next`: when `result.next.ready` is non-empty, write `Next: <key> — <title>` for its first entry and `Run /holycode-hub:claim <key>` (or `/holycode-hub:claim` with no argument), listing any other ready entries below it; when it is empty and `result.next.waiting` is not, say nothing is ready yet and list each waiting story's key with the keys and statuses in its `blocked_by`; when both are empty, say the backlog has no TODO story left. Never pick or suggest a story yourself. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" remove --key <story key>` and relay it: the worktree is removed, or it stays (with the reason) until its branch is pushed or merged — run the same command again then; with `sharedWith` it stays because those stories of the same group still work in it.
6. On `CONFLICT_ALREADY_COMPLETED` tell the user the story is already complete (never retry); on `FORBIDDEN_CLAIM` tell them they do not hold this story's lease (claim it first); on `BUSINESS_VERIFY_REQUIRED` tell them the story has no passed verify result in this claim — the Hub's message says whether none was submitted, the latest one failed or it asked for more evidence — run `/holycode-hub:verify <story key>`, address what it reports until it passes, then run this command again (never retry the completion as it is); on `BUSINESS_REPOSITORY_MISMATCH` tell them this story belongs to another repository of the project — the Hub's message names it — so its commit must come from a checkout of that repository: complete it from there (never retry from this checkout); on `BUSINESS_REPOSITORY_UNKNOWN` tell them the pointer's `**Repository ID:**` names no repository of this project — run `/holycode-hub:init` to record this repository again, then complete; on `BUSINESS_DOC_UPDATE_REQUIRED` tell them the story declared documentation it has not delivered, list the documents the error names (`details.missing`), offer to update and publish them as above, then complete again; on any other error report the code + request id and stop.
7. **Next step:** end your reply with one line that starts with `Next:` — the `Next:` line from `result.next` in step 5 — when both lists are empty, `Next: no TODO story is left — add one with /holycode-hub:add-scope`. Make no further Hub calls for this step.
