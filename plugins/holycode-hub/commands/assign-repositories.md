---
description: Propose a repository for every open story of a multi-repository project, review them when a repository is added, split stories that need two codebases and set each repository's stack — you confirm, then one batch writes them
argument-hint: [review [<repository name>]]
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps.
3. Call the `project_status` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>" }`. Take `result.project` (its `version` and `stack`), `result.project.repositories` (`id`, `kind`, `url`, `description`, `stack`; a repository's name is the last part of its URL, without `.git`) and every story row of `result.phases` (`id`, `key`, `title`, `status`, `version`, `repository_id`, with its phase and epic names). With no repository, say to run `/holycode-hub:init` in each repository first and stop; with exactly one, say its stories carry that repository automatically and stop. A story is **open** when its `status` is neither `COMPLETED` nor `IN_PROGRESS`; list the `IN_PROGRESS` (claimed) ones apart, as left for their holder, and never move, split or assign a claimed or completed story, and never propose to move or split a code-review ticket (a row whose `origin` is `CODE_REVIEW`): it belongs to the repository its finding was found in. The stories to propose for: every open story with no `repository_id`; and, when `$ARGUMENTS` starts with `review` (`review <repository name>` names the new repository; the newest one otherwise) or `/holycode-hub:init` just reported open stories on other repositories, also the open stories assigned to the other repositories — a review of whether they belong to the new one.
4. Read those stories' text (HH-497): call the `project_stories_text` tool on the `holycode-hub` MCP server with `{ "project_id": "<that id>", "story_ids": [<their row ids>] }` — at most 50 ids per call, as many calls as needed. Each answer carries per story its `title`, `description`, `acceptance_criteria` and `version` (use this `version` for the writes below); `not_open` names ids that were completed or deleted meanwhile — leave them out. Reading is recorded on the Hub (who read which story), takes no lease and counts toward no claim limit. On `403 FORBIDDEN_ROLE` (only an OWNER may read story text here — a DEVELOPER or VIEWER reads it through a claim) carry on **title-only**: say so once, and mark every proposal below `(title only)`.
5. For each of those stories propose ONE repository from its title, description and acceptance criteria (title only when step 4 fell back), its phase and epic names and the repositories' names, kinds and descriptions — by repository, never by kind alone: several backend services or several frontends are different repositories. Mark a proposal you are not sure of with `?`, and leave a story with no repository when it is not tied to code. When a story needs two codebases (for example an endpoint and the screen that calls it — read it from the description and acceptance criteria), propose a **split** instead: the original keeps its key and history and becomes the backend part, keeping the acceptance criteria that belong to it; a new story takes the other part — its own title, the acceptance criteria the original gives away (word for word) and its points — depends on the original and carries the other repository. In title-only mode, write the new part's criteria from the title and keep the original's criteria as they are. Also propose, for each repository whose `stack` is still the project's `stack`, its own stack from its kind and description (read this checkout when it is that repository) — none when the project's stack already fits.
6. Show the proposals grouped by repository as tables (key, title, proposed repository, `?`), then the splits (both parts with their criteria and points) and the stack proposals, and ask ONE confirmation; apply every change the user asks for. Nothing is written before that yes.
7. Write the confirmed assignments AND the confirmed splits together with the `project_story_repositories_set` tool — `{ "project_id": "<that id>", "assignments": [ { "story_id": "<row id>", "version": <its version>, "repository_id": "<id or null>" } ], "splits": [ { "from_story_id": "<original id>", "title": "…", "description": "…", "acceptance_criteria": ["…"], "points": <n>, "repository_id": "<the other repository>" } ] }`, at most 100 assignments and 20 splits per call. A split's original is one of the `assignments`, carrying its narrowed `title`, its kept `acceptance_criteria` (title-only mode: leave them out) and its `points`; the Hub creates the new part under the same epic, depending on the original, in the same transaction. All of a call is written or none: the Hub's message names the refused story (`assignments[<i>]` or `splits[<i>] (story <id>)`). On `409 CONFLICT_STALE_VERSION` that story changed meanwhile — run `project_status` again, show its new state, ask again and resend; on a `422` (`BUSINESS_STORY_CLAIMED`, `BUSINESS_STORY_COMPLETED`, `BUSINESS_REPOSITORY_UNKNOWN`, `BUSINESS_CODE_REVIEW_TICKET_REPOSITORY`) leave that story out, say why, and resend the rest. In title-only mode, name for each split which of the original's acceptance criteria now belong to the new story and ask the user to trim them (`/holycode-hub:add-scope edit <key>`). For each confirmed stack, call `project_update` with `{ "project_id": "<that id>", "version": <the project's current version>, "repository": { "id": "<repository id>", "stack": "<stack>" } }` — one call per repository, re-reading the project's version from `project_status` after each.
8. Report how many stories were assigned per repository, the splits made (both keys — the new one from the answer's `created`) and the stacks set, and anything left out with its reason. **Next step:** end your reply with one line that starts with `Next:` — `Next: /holycode-hub:status to see the board by repository`. Make no further Hub calls for this step.
