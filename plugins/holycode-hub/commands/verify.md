---
description: Submit a claimed Hub story's gate evidence and receive the Hub's verdict — run the local gate, assemble the evidence, call work_verify
argument-hint: <story-key>
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop.
3. Run the local gate (tests, coverage, lint, dependency audit) and the diff, then assemble the `evidence` object EXACTLY per the `work_verify` tool's input schema — `tests`, `coverage`, `lint`, `audit`, `diff`, `ac_table`, `status_matrix`, `attested`, `e2e` — from those real results. The Hub judges this evidence; it never runs your tests. Never fabricate a value to pass. For `status_matrix`: if the story touches an HTTP endpoint, report every required status code (200, 400, 401, 403, 404, 500) with whether it is directly tested; if the story owns NO endpoint (a frontend-only / pure-UI / library story), submit an empty `status_matrix: []` — the Hub treats that as not-applicable. When the story owns endpoints but NO endpoint in it can return a given code, report that code as `{ "code": <code>, "tested": false, "not_applicable": "<reason>" }` with the one reason it admits: `PUBLIC_ENDPOINT` for 401/403 (every endpoint the story owns is explicitly public — never for a protected one), `NO_DENIED_ROLE` for 403 only (the endpoints require sign-in but the story's `**Allowed Roles:**` lists every role, so no signed-in caller is refused), `NO_INPUT` for 400 (no body, params or query to reject), `NO_RESOURCE_LOOKUP` for 404 (no id or resource lookup). 200 and 500 are always tested. The Hub records each declaration as an attested claim the owner can review. Do NOT invent `tested: true` rows for codes with no endpoint behind them. For `e2e` (every story; a bug may omit it): when the story has its own E2E/browser test, run it and send `{ "status": "TESTED", "passed": <n>, "failed": <m> }` from that real run; when the story documents an E2E exemption, send `{ "status": "EXEMPT", "reason": "<the reason the story documents>" }` — the Hub records the reason as an attested claim the owner can review. Never report `TESTED` without having run the test, and never invent an exemption the story does not document.
4. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/effort-capture.mjs" take` — it prints the effort measured since the last report as a JSON array (timestamps, actor and category only); when it is non-empty add it as `"segments": <that array>` (omit the field when it prints `[]` or fails). Call the `work_verify` tool on the `holycode-hub` MCP server exactly once with `{ "project_id": "<that id>", "story_id": "$ARGUMENTS", "evidence": <that object> }` plus those segments.
5. On `VALIDATION_TOOL_INPUT` fix the evidence field named in the error and re-run; on `FORBIDDEN_CLAIM` tell the user to claim the story first (/holycode-hub:claim) and stop.
6. On a `result` report `verified.passed` and each `verified.checks` entry (name, passed, detail), the echoed `attested` claims and any `remediation`; if it did not pass, address the remediation and re-run (a fresh `attempt`), else the story is ready for /holycode-hub:complete. If `result.client_outdated` is present, first tell the user this plugin is outdated — installed `result.client_outdated.installed`, published `result.client_outdated.published` — and to update by running `/plugin marketplace update holycode-hub`, then `/plugin uninstall holycode-hub@holycode-hub`, then `/plugin install holycode-hub@holycode-hub`, then restarting Claude Code; an outdated plugin can lack instructions the Hub now expects.
7. Make no further Hub calls for this step.
