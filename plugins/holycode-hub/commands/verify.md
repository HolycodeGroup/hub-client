---
description: Submit a claimed Hub story's gate evidence and receive the Hub's verdict — run the local gate, assemble the evidence, call work_verify
argument-hint: <story-key>
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" check`: for each story worktree it lists as expired, tell the developer the lease lapsed and offer to re-claim the story (`/holycode-hub:claim <key>`) or keep its branch (`node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" keep --key <key>`) — never delete one yourself.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps.
3. **Gap analysis first** (every attempt, over the current change): follow the checklist in `${CLAUDE_PLUGIN_ROOT}/guidance-cache/gap-analysis.md` — when that file is missing, call the `work_guidance` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>", "question": "gap-analysis" }` and follow the returned topic. Hand the analysis to a subagent with a fresh context, so it does not review its own writing: give it the story's text and acceptance criteria (for a bug, the expected behaviour) from this session's claim — when they are not in context, run `/holycode-hub:claim $ARGUMENTS`, which renews the lease of a story you hold — the design (the `SCREENS` document read with the `project_documentation_read` tool, a Figma link or a design the story names) and the diff of this branch against the default branch, uncommitted changes included. Fix every gap it reports, re-run the affected tests, and analyse again until nothing new appears; a gap you leave on purpose is `ACCEPTED` with a reason a reviewer can check, never to pass. Send the result as `evidence.gap_analysis`: `{ "design": "ANALYSED" | "NO_UI_CHANGE" | "NO_DESIGN_REFERENCE", "findings": [ { "kind": "REQUIREMENT" | "DESIGN", "status": "FIXED" | "OPEN" | "ACCEPTED", "summary": "<one line>", "reason": "<for ACCEPTED>" } ] }` with every finding, fixed ones included — `NO_UI_CHANGE` only when no screen file changed (the Hub checks it against `diff.stat.files`), `NO_DESIGN_REFERENCE` when a screen changed but the story names no design; the Hub records each `ACCEPTED` finding and each declaration as an attested claim. Never report a gap analysis you did not run.
4. The project's own rules in `.project-management/rules/` are part of the gate: check the change against every file there as well as the gate criteria, and fix any conflict before submitting (on a conflict the project rules win over Hub guidance). Run the local gate (tests, coverage, lint, dependency audit) and the diff, then assemble the `evidence` object EXACTLY per the `work_verify` tool's input schema — `tests`, `coverage`, `lint`, `audit`, `diff`, `ac_table`, `status_matrix`, `attested`, `e2e`, `gap_analysis` — from those real results. The Hub judges this evidence; it never runs your tests. Never fabricate a value to pass. For `status_matrix`: if the story touches an HTTP endpoint, report every required status code (200, 400, 401, 403, 404, 500) with whether it is directly tested; if the story owns NO endpoint (a frontend-only / pure-UI / library story), submit an empty `status_matrix: []` — the Hub treats that as not-applicable. When the story owns endpoints but NO endpoint in it can return a given code, report that code as `{ "code": <code>, "tested": false, "not_applicable": "<reason>" }` with the one reason it admits: `PUBLIC_ENDPOINT` for 401/403 (every endpoint the story owns is explicitly public — never for a protected one), `NO_DENIED_ROLE` for 403 only (the endpoints require sign-in but the story's `**Allowed Roles:**` lists every role, so no signed-in caller is refused), `NO_INPUT` for 400 (no body, params or query to reject), `NO_RESOURCE_LOOKUP` for 404 (no id or resource lookup). 200 and 500 are always tested. The Hub records each declaration as an attested claim the owner can review. Do NOT invent `tested: true` rows for codes with no endpoint behind them. For `coverage`: report the measured per-file and repo-total numbers; only when NO changed file is source code (documentation, configuration, asset or test files only — for example a rule or README change, or a test that pins wording; a test file is any file under a `__tests__`, `test`, `tests`, `spec`, `e2e`, `cypress` or `integration_test` folder, or named `*.test.*`, `*.spec.*`, `*_test.*` or `test_*.py`) send `"coverage": { "not_applicable": "NO_SOURCE_CHANGE" }` instead — the Hub checks it against `diff.stat.files`, fails it next to any source file, and records it as an attested claim. Never invent coverage numbers. For `e2e` (every story; a bug may omit it): when the story has its own E2E/browser test, run it and send `{ "status": "TESTED", "passed": <n>, "failed": <m> }` from that real run; when the story documents an E2E exemption, send `{ "status": "EXEMPT", "reason": "<the reason the story documents>" }` — the Hub records the reason as an attested claim the owner can review. Never report `TESTED` without having run the test, and never invent an exemption the story does not document.
5. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/effort-capture.mjs" take` — it prints the effort measured since the last report as a JSON array (timestamps, actor and category only); when it is non-empty add it as `"segments": <that array>` (omit the field when it prints `[]` or fails). Also run `node "${CLAUDE_PLUGIN_ROOT}/scripts/effort-capture.mjs" usage` — it prints the tokens this attempt used so far, per model, as a JSON array (counts only, never prompt text); when it is non-empty add it as `"model_usage": <that array>` (omit the field when it prints `[]` or fails). Add how long the tests took as `evidence.timing` (HH-682) — optional and never part of the verdict, so leave out any part you could not measure and never estimate a number; all durations are whole milliseconds. `local`: `total_ms` for the whole local gate and `suites`, one entry per suite or workspace with its `name`, `kind` (`UNIT`, `INTEGRATION`, `E2E`, or `OTHER` for a run that mixes kinds) and `duration_ms` — read the time with `node -e "console.log(Date.now())"` before and after each run, or take the runner's own reported duration. `ci`: only when this branch has a pull request (`gh pr view --json number` succeeds) — take the pull request's head commit from `gh pr view --json headRefOid`, list its finished runs with `gh run list --commit <headRefOid> --event pull_request --status completed --json databaseId,workflowName` and pick the workflow that runs the tests (the CI workflow, not a labeler or scanner), then `gh run view <databaseId> --json jobs`, and send `run_id` (that databaseId), `total_ms` (the earliest `startedAt` to the latest `completedAt` across its jobs) and `jobs`, every job that ran with its `name` and `duration_ms` (`completedAt` − `startedAt`), matrix shards included (at most 50) — leave out skipped jobs that never started; leave `ci` out when there is no pull request, no finished run of the head commit or no `gh`. `slowest`: the 10 slowest test files of the local run, from the runners' JSON reports (Vitest `--reporter=json --outputFile=<file>`: each file's `endTime` − `startTime`; Playwright `--reporter=json`: the sum of each spec file's test durations; or the stack's equivalent), each with its `path` relative to the repository root (forward slashes, ending in the file's extension; leave out a file whose path does not fit) and `duration_ms` — file paths and numbers only, never test names, code or output. When this story accepted a speed-up task (HH-684 — its claim's `directive.maintenance`), the Hub checks this timing against the rule that fired: when the new run still fails that rule, add `evidence.speed_up`: `{ "reason": "<why, in words a reviewer can check>" }` — never invent a reason. Call the `work_verify` tool on the `holycode-hub` MCP server exactly once with `{ "project_id": "<that id>", "story_id": "$ARGUMENTS", "evidence": <that object> }` plus those segments and that model usage.
6. On `VALIDATION_TOOL_INPUT` fix the evidence field named in the error and re-run; on `FORBIDDEN_CLAIM` tell the user to claim the story first (/holycode-hub:claim) and stop.
7. On a `result` report `verified.passed` and each `verified.checks` entry (name, passed, detail), the echoed `attested` claims, any `remediation` and every `result.advisories` line (an early warning that never fails verify — for example declared documentation not updated yet, which /holycode-hub:complete will need); if it did not pass, address the remediation and re-run (a fresh `attempt`), else the story is ready for /holycode-hub:complete.
8. **Next step:** end your reply with one line that starts with `Next:` — build it from `result.next.step`: `COMPLETE` → `Next: /holycode-hub:complete <key>`; `FIX_AND_REVERIFY` → `Next: fix what the remediation names, then run /holycode-hub:verify <key> again`; `SEND_REQUESTED_DIFF` → `Next: run /holycode-hub:verify <key> again, adding diff.files for exactly the paths in wanted`. When `result.next` is absent (an older Hub), take it from `verified.passed` the same way. Make no further Hub calls for this step.
