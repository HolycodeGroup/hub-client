---
description: Claim a Hub story for implementation — story text, acceptance criteria, phase context, directive, project rules and command cards, and an 8-hour lease in one call
argument-hint: [story-key] | phase <name> | epic <name> | <story-key> <story-key> … | code-review [--severity critical,high]
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" check`: for each story worktree it lists as expired, tell the developer the lease lapsed and offer to re-claim the story (`/holycode-hub:claim <key>`) or keep its branch (`node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" keep --key <key>`) — never delete one yourself.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps. **Repository (HH-476):** when the pointer has no `**Repository ID:**` line, call the `project_status` tool on the `holycode-hub` MCP server once with `{ "project_id": "<that id>", "summary_only": true }` and pipe its JSON result into `node "${CLAUDE_PLUGIN_ROOT}/scripts/pointer-repository.mjs" resolve` (stdin): it compares this checkout's `origin` URL, credentials removed, with `project.repositories` on this machine — the URL is never sent — and adds the line. On `added` report the repository it recorded. On `no-match` (HH-489) ask the developer exactly ONE yes/no question — the answer's `question`, which names this checkout's repository, the project and the proposed kind `proposed_kind` (they may name another kind instead: BACKEND, FRONTEND, MOBILE or SHARED). On yes call the `project_repository_add` tool once with `{ "project_id": "<that id>", "kind": "<the confirmed kind>", "url": "<the answer's url>" }` and then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pointer-repository.mjs" record --id <the returned repository.id>`, and report the repository added — when it is the project's first repository, its stories without a repository take it. On no, add nothing and carry on without a repository. Never call `project_repository_add` without that yes. `present` and `no-origin` need no word.
3. Before anything is claimed (HH-679): when `$ARGUMENTS` names story keys (one, or several for a standing order), run `node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" busy --key <key> --tool claude-code` for each key; when one prints a `warning` (the other coding tool has a live session in that story's worktree), show the developer the `warning` exactly as printed and ask one question: Continue anyway / Stop; on Stop end this command here — no Hub call, nothing changed. Build `rule_cache`: if `.project-management/rules/.versions.json` exists, send `{ "project": { "<path>": <that entry's version> } }` (versions only — never text or hashes); omit `rule_cache` entirely when the file is missing. Build `command_cache`: if `${CLAUDE_PLUGIN_ROOT}/commands-cache/.manifest.json` exists, take its parsed contents verbatim, else omit it. Build `guidance_cache`: if `${CLAUDE_PLUGIN_ROOT}/guidance-cache/.manifest.json` exists, take its parsed contents verbatim, else send `{}`. Take `client_version` from the `version` field of `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` (omit it if that file cannot be read) — the Hub records it as your plugin version.
4. Call the `work_claim` tool on the `holycode-hub` MCP server exactly once with `{ "project_id": "<that id>", "story_id": "$ARGUMENTS", "rule_cache": <that object, when present>, "command_cache": <that object, when present>, "guidance_cache": <that object>, "client_version": "<that version, when present>", "repository_id": "<the pointer's **Repository ID:** value, when present>" }` — `repository_id` (HH-477) names the repository this checkout is: a claim without a key, and a standing order, then take only its stories and stories with no repository (omit it when the pointer has no such line) — `$ARGUMENTS` is a story key such as `DHWH-7` (an old story id also works); when `$ARGUMENTS` is empty, OMIT `story_id` entirely and the Hub claims the first story it lists as ready. **Standing order** — when `$ARGUMENTS` starts with `phase ` or `epic `, or names more than one story key, OMIT `story_id` and send `"scope"` instead: `{ "phase": "<the rest>" }`, `{ "epic": "<the rest>" }` or `{ "stories": [<each key>] }`; when `$ARGUMENTS` starts with `code-review`, OMIT `story_id` and send `"scope": { "origin": "CODE_REVIEW" }` — the project's code-review tickets — adding `"severity": [<each, UPPERCASE: CRITICAL, HIGH, MEDIUM, LOW>]` when `--severity <a,b>` follows (only tickets whose finding has one of them); the Hub claims the first ready story of that scope and hands out more of it, up to your concurrent-story limit. On `NOT_FOUND_SCOPE` show the error message and stop. On `BUSINESS_NO_CLAIMABLE_STORY` show the user the error message (it names what the backlog waits on) and stop. On `BUSINESS_STORY_COMPLETED` show the user the error message (the story is already done; pick a ready one from /holycode-hub:status) and stop — never retry it. The `result` is a JSON object with `story`, `context`, `directive` and `lease`; if it arrives as a text content block, parse that text as JSON first, then read the fields below off it.
5. Pipe the JSON of `result.directive.rule_deltas` into `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply-rule-deltas.mjs" --project-root "$PWD"` (stdin) and report its one-line summary; a non-zero exit means a delta was refused or a project file was skipped as an unsynced local edit (`project.conflicts`) — report it and suggest `/holycode-hub:sync`, never work around it.
6. Pipe the JSON of `result.directive.command_deltas` into `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply-command-deltas.mjs"` (stdin) and report its one-line summary; a non-zero exit means a card was refused — report it, never work around it. When `result.directive.guidance_deltas` is present, pipe its JSON the same way into `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply-command-deltas.mjs" --cache "${CLAUDE_PLUGIN_ROOT}/guidance-cache"`.
7. Tell the user which story they now hold — `result.story.key` and `result.story.title` — and to use that key in /holycode-hub:verify, /holycode-hub:complete and /holycode-hub:release (never the long id). When `result.story.code_review` is present (a ticket made from a Code Review finding), render right after the story text: "**Code review finding** — `<severity>` · `<file>:<line_start>-<line_end>` · `<report_url>`" (the location is where to read the code; the link opens the finding in Code Review — omit it when `report_url` is null). When `result.standing_order` is present, also list every `result.standing_order.handed_out` entry (`key — title`): the Hub has handed all of them to the user under this standing order; the response describes the first one, and `/holycode-hub:claim <key>` returns another one's text (it renews the lease, it is not a new claim). They may be worked in parallel (they are all unblocked), and each completion must pass the same scope (`/holycode-hub:complete <key> [commit-sha] --scope <the scope arguments>`) so the Hub hands out the next one; completing without it stops the standing order and releases nothing. When `result.standing_order.quota_reached` is present, show its `message`: a claim limit held more stories of the scope back — a report, never a failure. Tell them the lease expiry (`result.lease.expires_at`), that the directive is the knowledge for this step — story text, acceptance criteria, phase context, gate criteria and the `result.directive.guidance` entries (topic-keyed checklists: follow each one during implementation; an entry without its text is read from `${CLAUDE_PLUGIN_ROOT}/guidance-cache/<topic>.md`) are in the response — that the project's own rule deltas landed in this repository's `.project-management/rules/`, and the framework command cards in the plugin's `commands-cache/`. **Project rules come first:** before implementing, read every Markdown file in `result.directive.project_rules.directory` (`.project-management/rules/` — `result.directive.project_rules.files` names the ones the Hub holds) and apply them; on a conflict the project rules win over Hub guidance (`result.directive.project_rules.precedence`). **Another repository (HH-477):** when `result.repository_mismatch` is present, this story belongs to another of the project's repositories (`repository_mismatch.kind`, `repository_mismatch.url`) — the claim succeeded and the lease is the developer's, but this checkout is the wrong codebase: tell them so, create NO worktree here, skip step 8, and end with `Next: open a checkout of <repository_mismatch.url> and run /holycode-hub:claim <key> there` (claiming it again renews the lease and gives it a worktree in that repository). Otherwise give the story its own worktree: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" create --key <key> --title "<title>" --type <fix for a bug or a code-review story, else feat> --limit <result.lease.concurrent_limit> --expires <result.lease.expires_at> --tool claude-code` — under a standing order, when the `parallel-worktrees` guidance puts this story in the group of a story you already hold, add `--group <that story's key>` so it joins that worktree and branch instead of getting its own; on `ok: true` with a `warning` (the other coding tool still has a live session in that worktree) that the developer has not already answered with Continue anyway in step 3, show the developer the `warning` exactly as printed before any work and ask one question: Continue anyway / Stop; on Stop end this command here and change nothing (the lease stays held — `/holycode-hub:release <key>` returns it); on `ok: true` (after Continue anyway, or with no `warning`) tell the developer the worktree path and branch (and, with `group`, that it joined that story's group) and do all work for this story inside that directory; on `ok: false` relay its reason (the lease stays held — fix it and run this command again, or decline).
8. Then ask the developer one question before any work starts: **Start** this story, or **Decline** it (under a standing order, ask it for each handed-out story as it is picked up). For a code-review story (`result.story.code_review` present) the question is **Fix**, **Close as not-a-problem** or **Decline**: on Fix, continue as on Start; on Close as not-a-problem, first read the code at the finding's location in this repository and say what you found, then run `/holycode-hub:close <key> <resolution> <reason>` with an honest resolution and reason (never close a story just to clear the backlog). On Start, continue into implementation (then /holycode-hub:verify and /holycode-hub:complete). On Decline, ask for a one-line reason and run `/holycode-hub:release <key> <reason>` — the story goes straight back to the pool; the claim still counts toward the daily limit, because its text has already been shown. **Speed-up task (HH-684):** when `result.directive.maintenance` is present it is a separate maintenance task, never one of the story's acceptance criteria — show its `summary` as one line. When its `status` is `OFFERED`, ask the developer one more question: **Accept** it into this story, or **Defer** it to the next claim in this repository, and send the answer with one `work_progress` call `{ "project_id": "<that id>", "story_id": "<key>", "maintenance": { "id": "<maintenance.id>", "decision": "ACCEPT" | "DEFER" } }` — this answer is the one Hub call this step allows besides the claim; on Accept, follow `maintenance.guidance` within `maintenance.time_box_minutes` alongside the story. When its `status` is `ACCEPTED`, it is already part of this story. When its `status` is `PARKED`, show its `prompt` and, when `create_story_url` is not null, that link (the Create story button on the project's Effort tab) — omit the link when it is null. **Next step:** end your reply with one line that starts with `Next:` — on Start, `Next: implement the story against its acceptance criteria in the worktree, then run /holycode-hub:verify <key>`; on Decline, the release's own Next line. Make no further Hub calls for this step.
