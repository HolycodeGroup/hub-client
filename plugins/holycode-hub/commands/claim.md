---
description: Claim a Hub story for implementation — story text, acceptance criteria, phase context, directive, project rules and command cards, and an 8-hour lease in one call
argument-hint: [story-key] | phase <name> | epic <name> | <story-key> <story-key> …
---
1. Read `.project-management/hub-pointer.md` and take the value of its `**Project ID:**` line. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" check`: for each story worktree it lists as expired, tell the developer the lease lapsed and offer to re-claim the story (`/holycode-hub:claim <key>`) or keep its branch (`node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" keep --key <key>`) — never delete one yourself.
2. If the file is missing or has no project id, tell the user "No Hub project in this directory — run /holycode-hub:init" and stop. If any Hub call in this command answers 403 `FORBIDDEN_CREDENTIAL_ORG`, this sign-in belongs to a different organisation than this directory's project: show the Hub's message verbatim (it names the organisation), tell the user to sign in to the Hub again and choose that organisation on the Hub's organisation page (reconnect the `holycode-hub` MCP server so its sign-in opens — in Claude Code: `/mcp` → `holycode-hub` → re-authenticate), and stop — never repeat the call or switch to another project. If any Hub result in this command carries `client_outdated`, first tell the user this plugin is outdated — installed `client_outdated.installed`, published `client_outdated.published` — and to run `/holycode-hub:update`, then restart Claude Code; give no other update steps.
3. Build `rule_cache`: if `.project-management/rules/.versions.json` exists, send `{ "project": { "<path>": <that entry's version> } }` (versions only — never text or hashes); omit `rule_cache` entirely when the file is missing. Build `command_cache`: if `${CLAUDE_PLUGIN_ROOT}/commands-cache/.manifest.json` exists, take its parsed contents verbatim, else omit it. Build `guidance_cache`: if `${CLAUDE_PLUGIN_ROOT}/guidance-cache/.manifest.json` exists, take its parsed contents verbatim, else send `{}`.
4. Call the `work_claim` tool on the `holycode-hub` MCP server exactly once with `{ "project_id": "<that id>", "story_id": "$ARGUMENTS", "rule_cache": <that object, when present>, "command_cache": <that object, when present>, "guidance_cache": <that object> }` — `$ARGUMENTS` is a story key such as `DHWH-7` (an old story id also works); when `$ARGUMENTS` is empty, OMIT `story_id` entirely and the Hub claims the first story it lists as ready. **Standing order** — when `$ARGUMENTS` starts with `phase ` or `epic `, or names more than one story key, OMIT `story_id` and send `"scope"` instead: `{ "phase": "<the rest>" }`, `{ "epic": "<the rest>" }` or `{ "stories": [<each key>] }`; the Hub claims the first ready story of that scope and hands out more of it, up to your concurrent-story limit. On `NOT_FOUND_SCOPE` show the error message and stop. On `BUSINESS_NO_CLAIMABLE_STORY` show the user the error message (it names what the backlog waits on) and stop. On `BUSINESS_STORY_COMPLETED` show the user the error message (the story is already done; pick a ready one from /holycode-hub:status) and stop — never retry it. The `result` is a JSON object with `story`, `context`, `directive` and `lease`; if it arrives as a text content block, parse that text as JSON first, then read the fields below off it.
5. Pipe the JSON of `result.directive.rule_deltas` into `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply-rule-deltas.mjs" --project-root "$PWD"` (stdin) and report its one-line summary; a non-zero exit means a delta was refused or a project file was skipped as an unsynced local edit (`project.conflicts`) — report it and suggest `/holycode-hub:sync`, never work around it.
6. Pipe the JSON of `result.directive.command_deltas` into `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply-command-deltas.mjs"` (stdin) and report its one-line summary; a non-zero exit means a card was refused — report it, never work around it. When `result.directive.guidance_deltas` is present, pipe its JSON the same way into `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply-command-deltas.mjs" --cache "${CLAUDE_PLUGIN_ROOT}/guidance-cache"`.
7. Tell the user which story they now hold — `result.story.key` and `result.story.title` — and to use that key in /holycode-hub:verify, /holycode-hub:complete and /holycode-hub:release (never the long id). When `result.standing_order` is present, also list every `result.standing_order.handed_out` entry (`key — title`): the Hub has handed all of them to the user under this standing order; the response describes the first one, and `/holycode-hub:claim <key>` returns another one's text (it renews the lease, it is not a new claim). They may be worked in parallel (they are all unblocked), and each completion must pass the same scope (`/holycode-hub:complete <key> [commit-sha] --scope <the scope arguments>`) so the Hub hands out the next one; completing without it stops the standing order and releases nothing. When `result.standing_order.quota_reached` is present, show its `message`: a claim limit held more stories of the scope back — a report, never a failure. Tell them the lease expiry (`result.lease.expires_at`), that the directive is the knowledge for this step — story text, acceptance criteria, phase context, gate criteria and the `result.directive.guidance` entries (topic-keyed checklists: follow each one during implementation; an entry without its text is read from `${CLAUDE_PLUGIN_ROOT}/guidance-cache/<topic>.md`) are in the response — that the project's own rule deltas landed in this repository's `.project-management/rules/`, and the framework command cards in the plugin's `commands-cache/`. Then give the story its own worktree: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/story-worktree.mjs" create --key <key> --title "<title>" --type <fix for a bug, else feat> --limit <result.lease.concurrent_limit> --expires <result.lease.expires_at>` — under a standing order, when the `parallel-worktrees` guidance puts this story in the group of a story you already hold, add `--group <that story's key>` so it joins that worktree and branch instead of getting its own; on `ok: true` tell the developer the worktree path and branch (and, with `group`, that it joined that story's group) and do all work for this story inside that directory; on `ok: false` relay its reason (the lease stays held — fix it and run this command again, or decline).
8. Then ask the developer one question before any work starts: **Start** this story, or **Decline** it (under a standing order, ask it for each handed-out story as it is picked up). On Start, continue into implementation (then /holycode-hub:verify and /holycode-hub:complete). On Decline, ask for a one-line reason and run `/holycode-hub:release <key> <reason>` — the story goes straight back to the pool; the claim still counts toward the daily limit, because its text has already been shown. **Next step:** end your reply with one line that starts with `Next:` — on Start, `Next: implement the story against its acceptance criteria in the worktree, then run /holycode-hub:verify <key>`; on Decline, the release's own Next line. Make no further Hub calls for this step.
